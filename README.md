# fineprint

A question-answering service over the official U.S. government handbook "Medicare & You 2026",
which answers in plain language and cites the handbook page it used. It is a portfolio project
about production RAG engineering: hybrid retrieval, a verified golden set, per-call observability,
LLM-as-judge evaluation, and an eval gate in CI.

## Why this project exists

Most retrieval demos stop at "it answered my question". This one is built around the harder
question: how good is the retrieval, and how would you know? The engineering is the subject.

- Hybrid retrieval — lexical search and vector similarity, fused with reciprocal rank fusion —
  rather than vector search alone.
- A golden set of questions a beneficiary or their adult child would actually ask, each with an
  expected answer and expected source pages taken from the PDF rather than guessed.
- Observability on every LLM and tool call, with cost and latency.
- An LLM judge calibrated against hand labels instead of trusted on faith.
- An eval gate in CI that blocks a pull request which makes answers worse.

Every part of the series ends with measured numbers, produced by a script and committed next to the
code that produced them.

## Part 1 — the RAG service

### What was built

Ingestion turns the pinned PDF into rows. `fineprint ingest` checks the file against its recorded
sha256, extracts one text block per page with pypdf, cuts the whole book into overlapping windows
of 220 words that each remember the pages their first and last word came from, asks Amazon Titan
Text Embeddings v2 for a 1024-number vector per window, and writes documents, pages and chunks to
Postgres in one transaction. Re-running replaces that edition's rows for that chunk set rather than
adding a second copy. Nothing at question time opens the PDF.

Retrieval runs two searches over the same table. The lexical one matches the question's words
against each chunk's stored `tsvector`, ranked by Postgres's `ts_rank_cd`; the question is turned
into an OR query of its own lexemes, because a natural-language question as an AND query returns
nothing the moment one word is missing. The vector one embeds the question and orders chunks by
cosine distance with pgvector. Reciprocal rank fusion then merges the two ranked lists by
*position* rather than by score — `ts_rank_cd` values and cosine similarities are on different
scales and adding them would be meaningless — and the top 5 survivors go to the model. Each result
carries where it stood in each list, so `/search` can show why a passage is there.

Answering is where the checking happens. The model never sees or produces a page number: each
excerpt arrives wrapped as `<chunk id="61" pages="23">…</chunk>`, and Claude Opus 5 answers by
calling a single tool whose input schema is the JSON schema of the draft answer, which the service
then validates with Pydantic. It drops any citation naming a chunk that was not retrieved and
counts the drops, fills in every page number from the database rows, and marks each quote verified
or not by looking for it in that chunk's own text. An unverified quote is still shown, marked
unverified, because hiding it would hide the failure. When the excerpts do not contain the answer
the model sets `found_in_handbook` to false and points at Medicare.gov, 1-800-MEDICARE, the State
Health Insurance Assistance Program or Social Security; that is a successful answer, not an error.

Around all of that: a FastAPI service with `POST /search`, `POST /ask` and `GET /healthz`, a
`fineprint` command with `init-db`, `ingest`, `search`, `ask` and `serve`, a golden set of 40
questions whose every evidence quote is checked against the extracted PDF text, and the three eval
programs — the runner, the manual review tool, and the scoreboard generator that writes both
`evals/scoreboard.md` and the block above.

```
                     fineprint ingest (once)

  handbook.pdf ──▶ pages ──▶ 220-word chunks ──▶ Titan embeddings
                                    │
                                    ▼
                    Postgres 16 · tsvector + vector(1024)
                                    │
  question ─┬─▶ lexical search (Postgres FTS) ──┐
            │                                   ├─▶ RRF ─▶ top 5 chunks
            └─▶ embed ─▶ vector search (cosine) ┘              │
                                                               ▼
                                                 Claude Opus 5, one tool call
                                                               │
                                                               ▼
                                          answer · citations · confidence
                                    pages come from the database, quotes checked
```

There is no ORM and no RAG framework anywhere in `src/fineprint/`: plain Python, plain SQL, and one
thin provider abstraction, which is where part 3 added timeouts, retries and a fallback to a second
model on the same provider.

### Run it end to end

Prerequisites:

- [uv](https://docs.astral.sh/uv/) and Docker.
- An AWS account with Amazon Bedrock access to **three** models: `us.anthropic.claude-opus-5`,
  `amazon.titan-embed-text-v2:0` and `cohere.rerank-v3-5:0`, in the region you configure below, and
  credentials for it in your environment. The re-ranker is called because `.env.example` turns it
  on, as the best configuration on the part 2 scoreboard. Every model call goes to Bedrock, so
  there is no separate API key to obtain and no model runs on your machine.

Nothing below needs any state you do not create here.

```bash
git clone https://github.com/vmural9/fineprint.git
cd fineprint
uv sync                                       # create the virtualenv and install everything
```

Copy `.env.example` to `.env` and set `AWS_REGION` to the region you have those three models enabled
in. The rest of the file already matches `docker-compose.yml`, so on a local machine there is
nothing else to change. It sets `CHUNK_SET=sections` and `RERANKER_PROVIDER=bedrock`, the best
configuration on the part 2 scoreboard, which is not the default in `src/fineprint/config.py`.

Credentials are the one thing `.env` cannot supply. The AWS SDK reads the credential chain from the
process environment, not from this project's `.env`, so **export `AWS_PROFILE` in the shell you run
these commands in** — or export the access keys, or leave it unset to use your default profile.
Credentials themselves never go in a file in this repository.

```bash
cp .env.example .env
$EDITOR .env                                  # AWS_REGION=us-west-2, if that is not your region
export AWS_PROFILE=your-bedrock-profile       # boto3 reads this from the environment, not .env
```

Start Postgres, fetch the corpus, create the schema, and load the handbook. `ingest` is the first
step that spends anything: one small embedding call per chunk, run in parallel, which takes
seconds. It verifies the PDF's sha256 and the embedder's output width before it calls anything, so
a run that cannot work costs nothing.

```bash
docker compose up -d --wait                   # Postgres 16 with pgvector on localhost:5432
uv run python scripts/download_handbook.py    # fetch and hash-verify the handbook into data/raw/
uv run fineprint init-db                      # create the tables and indexes; safe to repeat
uv run fineprint ingest --chunk-set fixed-220w   # part 1's chunks, which the part 1 evals read
uv run fineprint ingest --chunk-set sections     # the chunks the service reads; both are safe to repeat
```

Now ask it things. `search` shows what retrieval finds with no model in the way, which is how a bad
answer is diagnosed; `ask` adds the answer and the citation check.

```bash
export CHUNK_SET=fixed-220w RERANKER_PROVIDER=none   # part 1's setup, for the comparison below
uv run fineprint search "How much is the Part B premium in 2026?" --mode hybrid
uv run fineprint search "How much is the Part B premium in 2026?" --mode vector
uv run fineprint search "How much is the Part B premium in 2026?" --mode lexical
unset CHUNK_SET RERANKER_PROVIDER                    # back to the values in .env

uv run fineprint ask "How much is the Part B premium in 2026?"

# q040 from the golden set, which the handbook does not answer: this one abstains and
# points you somewhere that does know.
uv run fineprint ask "How much would a Medigap Plan G policy cost my dad per month?"
```

Running that first question in all three modes shows what fusion does to a ranking: vector search
puts the chunk carrying the standard Part B premium first, and the hybrid drops it to third behind
two chunks that both retrievers returned. Page 23 still comes back at rank 1 in all three modes, so
nothing is lost here — the question where fusion actually loses a page is `q034`, described under
["What the numbers say"](#what-the-numbers-say).

The same two operations over HTTP, plus a health check that tells "up" from "up but empty":

```bash
uv run fineprint serve                        # http://127.0.0.1:8000, schemas at /docs
```

Then, in another shell:

```bash
curl http://127.0.0.1:8000/healthz
curl -X POST http://127.0.0.1:8000/search \
  -H 'content-type: application/json' \
  -d '{"query": "How much is the Part B premium in 2026?", "mode": "hybrid", "top_k": 5}'
curl -X POST http://127.0.0.1:8000/ask \
  -H 'content-type: application/json' \
  -d '{"question": "How much is the Part B premium in 2026?"}'
```

Then the evals. The first command answers all 40 questions with Claude Opus 5 and is the expensive
one. The other two skip the answer model, but `vector-only` still embeds each question through
Bedrock; `lexical-only` is the only configuration that calls no model at all, and so the only one
that is free and runs offline.

```bash
uv run python -m evals.run_golden_set --config hybrid
uv run python -m evals.run_golden_set --config vector-only --retrieval-only
uv run python -m evals.run_golden_set --config lexical-only --retrieval-only
uv run python -m evals.review evals/results/<run_id>.json    # your own pass or fail per answer
uv run python -m evals.scoreboard                            # regenerate both tables
```

Each run writes `evals/results/<UTC timestamp>_<config>.json`, recording the commit, the whole
configuration, the corpus and golden-set hashes, and every question's retrieved chunks, metrics and
answer. `evals/scoreboard.md` and the block above are generated from the latest results file of
each configuration and are never edited by hand; `python -m evals.scoreboard --check` writes
nothing and exits non-zero when either file is out of date, which is what stops a number from being
typed in. `evals/README.md` documents the golden set and the metrics.

The checks that run on every change, none of which needs AWS or the network:

```bash
uv run ruff check . && uv run ruff format --check .
uv run pytest                                          # integration tests need Postgres up
uv run python -m evals.verify_golden_set               # re-check every evidence quote against the PDF
uv run python -m evals.scoreboard --check
```

### What the numbers say

This section compares three of the scoreboard's rows: `hybrid`, `vector-only` and `lexical-only`,
the three on the naive fixed-size chunker without a re-ranker. They are runs over the same 40
questions and the same pinned PDF, at k = 5, 20 candidates per retriever, RRF k = 60. Retrieval
metrics are computed over the answerable questions only; an unanswerable question has no expected
pages, and what it measures is abstention. The results files are in `evals/results/`, and the
scoreboard recomputes every aggregate from their per-question rows.

**The hybrid does not win — by one question.** Vector-only retrieval gets 88.2% on Page hit@5; the
hybrid gets 85.3%. That 2.9-point gap is a single question out of the 34 answerable ones, decided
by a tie-break, so it is a worked example of how fusion can hurt rather than evidence that it
usually does. The secondary metrics point the same way with a little more behind them:
`page_recall@5` is 88.2% for vector-only against 82.4% for the hybrid — three expected pages out of
45, across three questions — and `mrr` is 0.86 against 0.77. On this golden set, at this size,
fusion did not earn its place; whether that would survive a bigger set is not a conclusion part 1
is entitled to.

Here is the mechanism behind that one question. RRF scores a chunk by its position in each list it
appears in and adds those scores up, so a chunk both retrievers returned outranks a chunk only one
of them returned. That is the behaviour you want when both lists are good, and exactly the
behaviour that cost a page here: agreement with a weak lexical list was worth more than being first
in the strong one. Question `q034` — "Mom has a high income and gets her drug
coverage through a Medicare Advantage plan. Does she still owe the Part D extra charge, and does
she pay it to the plan?" — shows it cleanly. The answer is on page 82. Vector search put chunks
from page 82 at the top of its list; lexical search did not return page 82 anywhere in its 20
candidates. The hybrid's top 5 was then made of chunks that both lists had returned somewhere,
plus lexical's own first result, and page 82 was gone. It is the only question in the run where
vector-only found the page and the hybrid did not, there is no question where the trade went the
other way, and that single question is the whole gap between the two rows.

**The lexical leg is the weakest part of the system**, at 67.6% against the vector leg's 88.2%, with
`mrr` 0.56 against 0.86. Postgres full-text ranking here is `ts_rank_cd`, a coverage-density score
and not BM25 — the `pgvector/pgvector:pg16` image ships no BM25 extension — and the chunks it
ranks still contain running headers, the table of contents and the five-page index, because part 1
is deliberately the naive baseline.

**Plain lookups are the weakest question type**, which is not where you would expect a naive
retriever to fail. For the hybrid, `page_hit@5` by type is 100.0% on the 10 `multi_section`
questions, 88.9% on the 9 `table` questions, and 73.3% on the 15 `lookup` questions. Vector-only
shows the same shape: 100.0%, 88.9%, 80.0%. The likely reason is that a lookup is short and
specific and often phrased in the reader's words rather than the handbook's — "will Medicare buy
him a wheelchair" against a passage headed "durable medical equipment" — while a multi-section
question is long enough to overlap the handbook's vocabulary somewhere. Part 2 measures what
chunking and re-ranking do to lookups; it does not test this explanation directly.

**The answers hold up where retrieval does.** `cited_page_hit` is 85.3% — the same as the hybrid's
page hit rate, and on the same questions: whenever an expected page was retrieved, the answer cited
it, and whenever one was not, it did not invent one. `abstention_accuracy` is 87.5%, five errors in
40, and four of them run the same way: the service said "the handbook doesn't say" about a question
the handbook does answer. In every one of those four, retrieval had already failed — three missed
the expected page outright, and the fourth, `q029`, needed pages 18 and 80 and got only 80, so the
model refused on exactly the half it had not been shown. None of the four is the model discarding
evidence it was given. The fifth is the one error retrieval does not explain, and it runs the other
way. `q026` asks exactly how many dollars Dad will owe for a hernia repair in a hospital outpatient
department, which the handbook does not say. Retrieval had not failed on it: the top two passages
were the page 47 text that gives the general rule for outpatient costs and points to
Medicare.gov/procedure-price-lookup. The answer's text says what the golden set's expected answer
says — no dollar figure for a specific procedure, the general rule, and that price-lookup tool —
but the model also set `found_in_handbook` to true, with `confidence` high. That flag is what
`abstention_accuracy` scores, so on this question the service claimed the handbook answers
something it does not.

**Manual pass is the one hand-made number.** `page_hit@5` measures whether the right page came
back, and `cited_page_hit` whether the answer pointed at it; neither can say whether the sentence
built from that page is *correct*. That judgement is the reviewer's: I graded all 40 `hybrid`
answers with `python -m evals.review`, judging each written answer as a reader would, and the
scoreboard's 85.0% comes from those verdicts. Each failing answer is a retrieval miss or a half
answer, and the note stored with its verdict says which. Part 4 reuses these same labels to
calibrate its LLM judge rather than creating new ones.

**What part 2 did with this.** Part 1 left three openings: whether fusion can be made to earn its
place (weighting the legs, or a re-ranker over the fused candidates, instead of trusting
agreement); whether the lexical leg improves more from a real BM25 extension or from stripping the
headers, the contents and the index out of the chunks; and whether structure-aware chunking closes
the gap on `lookup` questions. Part 2 measured the first with a re-ranker and the third with the
`sections` chunker, on this same golden set and in the same table, beside these rows; its findings
are [below](#findings). The second was not part of part 2, and the lexical leg is unchanged.

## Part 2 — retrieval quality

### What was built

Part 1 judged retrieval by one coarse question: was an expected page among the five passages? Part 2
changes retrieval in two ways, one at a time and then together, and scores every configuration with
four metrics that read the text itself.

**A chunker that follows the handbook.** Part 1's `fixed-220w` chunker cuts overlapping windows
of 220 words wherever the count falls, so a window can stop in the middle of a sentence or a table.
The new `sections` chunker cuts where the handbook itself changes subject, at its headings, and
keeps every table whole in one chunk. The prose under a heading is packed into chunks of at most 300
words (`max_words=300`); a paragraph is split only when it is longer than that, and then between
sentences. The heading rides at the head of its section's first chunk, and every chunk records the
heading it sits under, such as "Section 1: Signing up for Medicare > How much does Part B coverage
cost?". The chart comparing Original Medicare with Medicare Advantage on pages 11–12 is a single
`sections` chunk, where `fixed-220w` spreads it across several windows. Both chunk sets live in the
database side by side, and `fineprint chunks --page 11 --chunk-set <name>` prints how either one
cuts a page. How headings and tables are recognised in pypdf's text is written out in the docstring
of `src/fineprint/chunking.py`.

**A re-ranker.** A re-ranker is a second model that reads the question together with each candidate
passage and scores how well the passage answers it. That is slower than the two searches that find
the candidates, so it only reads a shortlist. Here it is Cohere Rerank 3.5 on Amazon Bedrock
(`cohere.rerank-v3-5:0`), behind the same thin provider interface as the other two models: it
re-scores the top 20 of the fused list, and the best 5 by its score are kept, in its order. Each
chunk keeps its fused rank beside its new one, so the results files, and `fineprint search` run with
`RERANKER_PROVIDER=bedrock`, show what the re-ranker moved. Only hybrid retrieval is re-ranked;
`vector` and `lexical` exist to measure one retriever alone.

**Four metrics that read the text.** Page hit says whether the right page came back, not whether the
passage holds the answer or whether the answer keeps to it. Part 2 adds the four RAGAS metrics.
RAGAS, short for Retrieval Augmented Generation Assessment, is a published framework for scoring a
RAG system's retrieval and its answers with a language model as the judge; the four are implemented
here from their definitions in the RAGAS paper and documentation, in `evals/ragas_metrics.py`, where
every prompt and formula is written out. A model reads and plain Python counts: the judge is
Claude Sonnet 5, a different model from Claude Opus 5, which writes the answers, so no answer is
graded by its author.

- **Context recall**: did retrieval find what the answer needs? The expected answer is split into
  sentences, the judge says for each whether the retrieved passages support it, and the score is the
  supported share.
- **Context precision**: did retrieval put the useful passages first? The judge marks each passage
  useful or not for reaching the expected answer, and the score averages, over the ranks *k* that
  hold a useful passage, the share of useful passages among the first *k*: a useful passage counts
  for more the higher it sits, and a list with none scores 0.
- **Faithfulness**: does the answer keep to its passages? The judge lists the answer's factual
  claims, then checks each one against the passages, and the score is the supported share.
- **Answer relevance**: does the answer address the question asked? The judge, shown only the
  answer, writes questions it would answer completely, and the score is the mean cosine similarity
  of their Titan embeddings to the embedding of the question actually asked. An answer the judge
  calls noncommittal, one that says the information is not available, scores 0.

The six questions the handbook does not answer are excluded from all four: their expected answer is
that the handbook does not say, which leaves no facts for recall or precision to find, and an
abstention makes no claims to check. Excluded means left out of the mean, not scored 0;
`abstention_accuracy` remains their measure. An answer that makes no factual claim has no
faithfulness score either. And a judged score is an estimate with its own error, not a count like
page hit; part 4 will calibrate the judge against hand labels.

**The scoring pass.** Scoring is a second pass over a finished run.
`python -m evals.score evals/results/<run_id>.json` reads each question's passages from the results
file, never from the database, whose chunks can be re-ingested after a run. It has the judge score
every answerable question and writes the four scores into the same file beside the page metrics,
together with every verdict behind them: each sentence, passage and claim, the judge's yes or no,
and its one-line reason. The file also records the judge model, the embedding model and a hash of
the prompts, which ties each score to the prompt text that produced it. `--explain QID` prints the
working behind one question's four numbers.

**The candidate diagnostic, run before the re-ranker.** A re-ranker can only promote a passage that
retrieval has already put in front of it. So before any re-ranked run, `python -m evals.candidates`
took the whole fused list for every answerable question, before the top-5 cut, and recorded where
the first chunk covering an expected page sat. That turned "a re-ranker should help" into a
prediction with question ids in it: on `fixed-220w`, four of the hybrid's five misses, `q034`,
`q035`, `q021` and `q031`, had their page at fused ranks 6 to 20, inside the shortlist the re-ranker
reads, and the fifth, `q019`, had it at rank 39, out of its reach. The diagnostic's files are in
`evals/results/candidates/`.

**Six configurations**, defined in `evals/configs.py`: part 1's three under their old names, plus a
two-by-two of chunk set and re-ranker in hybrid mode, so each change is measured alone and together
with the other.

| Configuration | Chunk set | Retrieval | Re-ranker |
|---------------|-----------|-----------|-----------|
| `hybrid` | `fixed-220w` | hybrid | none |
| `hybrid+rerank` | `fixed-220w` | hybrid | Cohere Rerank 3.5 |
| `sections` | `sections` | hybrid | none |
| `sections+rerank` | `sections` | hybrid | Cohere Rerank 3.5 |
| `vector-only` | `fixed-220w` | vector | none |
| `lexical-only` | `fixed-220w` | lexical | none |

**Hypotheses, committed first.** Before any part 2 run I wrote down what I expected each change to
do, why, and, where I could, which question it should fix, and committed that as
`evals/HYPOTHESES.md`; the file has not been edited since. Written first, a prediction can fail in
public. Written after the numbers, almost any result can be explained, and the hypothesis tends to
be the one that held. The findings below judge each one held, partly held or not held, the three
verdicts that file fixes.

### Run it end to end

Part 2 runs on part 1's setup and needs two more models enabled in the same Bedrock region:
`us.anthropic.claude-sonnet-5`, the judge, and `cohere.rerank-v3-5:0`, the re-ranker. As in part 1,
export `AWS_PROFILE` in the shell you run these commands in; boto3 reads it from the environment,
not from `.env`.

```bash
export AWS_PROFILE=your-bedrock-profile          # boto3 reads this from the environment, not .env
uv run fineprint ingest --chunk-set sections     # the second chunk set, stored beside fixed-220w
uv run fineprint chunks --page 11 --chunk-set fixed-220w   # one page cut both ways; reads the
uv run fineprint chunks --page 11 --chunk-set sections     # database and calls no model

uv run python -m evals.candidates --chunk-set fixed-220w --mode hybrid   # where each expected
uv run python -m evals.candidates --chunk-set sections --mode hybrid     # page sits in the pool

uv run python -m evals.run_golden_set --config hybrid+rerank   # or any name in evals/configs.py
uv run python -m evals.score evals/results/<run_id>.json       # the judge's pass, into that file
uv run python -m evals.score evals/results/<run_id>.json --explain q034   # one question's working
uv run python -m evals.scoreboard                              # regenerate both tables
```

Every configuration answers all 40 questions with Claude Opus 5, and the scoring pass then makes
several judge calls per question, plus embedding calls for answer relevance, so neither a run nor a
scoring pass is free; `evals/README.md` counts the calls. The candidate diagnostic embeds each
question once and calls no answer model, and `--explain` on a scored question reads the file and
calls nothing. To watch the re-ranker on one question,
`RERANKER_PROVIDER=bedrock uv run fineprint search "<question>"` prints each chunk's fused rank
beside its new one.

## Part 3 — observability and agent

### What was built

Parts 1 and 2 made the service answer and measured how well. Neither recorded what happens inside
one request: which calls it made, how long each took, what each cost, and what the service did
when a call failed. Part 3 adds that, and then puts a small agent on top of the retriever, so that
the figures a question needs are looked up rather than remembered.

**Tracing.** A *trace* is the record of one request, made of *spans*, one per call that matters.
The service traces every model call (the answer, each embedding, each re-rank, each turn of the
agent) and every tool call, and for each it keeps the tokens used, the cost at list prices, and the
time it took. Spans nest the way the calls do:

```
agent                          one question
├─ search                      the retriever
│   ├─ embed_query             Titan: tokens, cost
│   └─ rerank                  Cohere Rerank 3.5: search units, cost
└─ tools                       the agent's turns
    ├─ turn                    Claude Opus 5: tokens, cost; asks for tools
    ├─ lookup_cost_figure      local code: arguments, result, time
    ├─ lookup_cost_figure
    └─ turn                    Claude Opus 5: the call that records the answer
```

A question asked through `/ask`, `/agent` or `/search`, or through the `fineprint` command, opens
one such trace. In an eval run each of the 40 questions is a trace, tagged `eval` and with the
configuration's name, and a run's 40 traces are grouped under the run's id. The same spans are
always kept in the process as a record of the question (`TraceRecord` in
`src/fineprint/tracing.py`), whether or not anything is sent anywhere, so cost and latency never
depend on a call to Langfuse. An eval run writes that record into its results file beside each
question, and the scoreboard's cost and latency columns are computed from it. `fineprint ask`
and `fineprint agent` print what the question cost, and `/ask` and `/agent` return the trace's id
and cost.

Cost is worked out when a call returns, from the tokens it used (or, for the re-ranker, its
search units) and the AWS list price in `us-west-2`. `src/fineprint/pricing.py` holds each price,
the AWS price list it was read from and the date. Langfuse's own price table is not used. A call
whose price is not in that table has no cost, and a trace containing one has no cost either; an
unknown amount is never added up as zero.

**Turning tracing on.** `TRACING_PROVIDER=none` is the default: nothing leaves the process, and
cost and latency are still measured. To send traces to Langfuse, set `TRACING_PROVIDER=langfuse`
and the three values from a Langfuse project's settings page in `.env`: `LANGFUSE_PUBLIC_KEY`,
`LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL`, the region URL. `Settings` refuses to build with
`langfuse` and any of the three missing, and `GET /healthz` says which mode the service is in. I
used Langfuse Cloud on its free Hobby plan; the traces hold handbook text and golden-set questions
and nothing private. `langfuse` is imported in one module of the service only,
`src/fineprint/langfuse_sink.py`, which turns the service's spans into Langfuse observations;
everything else talks to a small `Sink` interface, so the tests use a recording stand-in and a
plain `pytest` never reaches the network.

**Retries, timeouts and fallback.** Every model call has an explicit timeout and a bounded number
of retries, all settings in `.env`:

| Call | Timeout | Retries | When it still fails |
|------|---------|---------|---------------------|
| Answer model, Claude Opus 5 | `LLM_TIMEOUT_SECONDS=60` per request | `LLM_MAX_RETRIES=4`, the SDK's, for throttling and server errors | Falls back to Claude Sonnet 5 on Bedrock (`FALLBACK_LLM_MODEL`), only when the failure is a timeout or the model being unavailable. The answer says it came from the fallback and names the model. A refusal, a cut-off reply, a malformed tool call or a 4xx other than 429 does not fall back: it would happen again. |
| Embedder, Titan | `AWS_TIMEOUT_SECONDS=10` read, 5 connect | `AWS_MAX_ATTEMPTS=4`, botocore's standard mode, first try included | No fallback, by construction: another embedding model would not match the stored vectors. The request fails, and the API answers 503. |
| Re-ranker, Cohere Rerank 3.5 | `AWS_TIMEOUT_SECONDS=10` read, 5 connect | `AWS_MAX_ATTEMPTS=4` | Degrades: the fused order is used and the response says it was not re-ranked. |
| The two tools | none; local code | none | The error goes back to the model as the tool's result, and the trace records it. |

With the defaults, the slowest path to the fallback is five requests of up to 60 seconds each
(1 + 4). There is no circuit breaker: the fallback is per call, and the next call tries the
primary again, which is all that "recover" means here.

`FAULT_INJECTION` makes a call fail on purpose so that this behaviour can be shown and tested. It
takes `<target>:<fault>` or `<target>:<fault>:once`, with target `chat`, `embedding` or `rerank` and
fault `unavailable` or `timeout`; `chat:unavailable:once` makes the first answer fall back and the
next one go to Opus again. It raises the same errors the Bedrock classes do, before the real model
is called, so nothing is billed, and the failure appears in the trace like a real one. It is empty
by default, and `evals.run_golden_set` refuses to start while it is set, because a measured run
must not have injected faults in it.

**The agent.** `answer_question` hands the model the retrieved passages and takes one answer back.
That is enough when the answer is a sentence the handbook prints. It is not enough when the answer
has to be worked out, and a model doing arithmetic in its head, or remembering last year's amount,
writes a figure that looks right and is not. So `answer_with_tools` (in `src/fineprint/agent.py`;
the `fineprint agent` command, `POST /agent` and the `agent` configuration all call it) gives
Claude Opus 5 the same retrieved passages and two tools, both plain Python that calls no model, no
network and no database:

- **`lookup_cost_figure`** returns one of the 2026 dollar amounts the handbook prints, with the
  page and the sentence it comes from. The table holds eleven amounts (the Part B premium and
  deductible, the Part A deductible and hospital coinsurance, the Part D out-of-pocket cap, and so
  on), each copied from the pinned printing. The tool's argument is a fixed list of those figures,
  so the model cannot ask for an amount the handbook does not print.
  *Example, q023: "Dad has been an inpatient in the hospital for 80 days straight in the same
  benefit period. What is he paying per day now, and what happens if he's still there past 90
  days?"* The agent made two calls, `part_a_coinsurance_days_61_90` and
  `part_a_coinsurance_lifetime_reserve_days`, and got back "$434 per day, page 27, *Days 61–90: You
  pay $434 each day*" and "$868 per day, page 27". Its answer says that day 80 falls in days
  61–90, so $434 each day; that days 91–150 cost $868 each day while he uses his 60 lifetime
  reserve days; and that after day 150 he pays all costs.
- **`check_enrollment_window`** works out, from a birth date and a reference date, when the
  Initial Enrollment Period starts and ends and when coverage would begin, using the rules on
  pages 17 and 18 and nothing else. The reference date is `as_of`; when the model leaves it out
  it is the service's own date, and the eval runner pins it to the run date and records it in the
  results file, so a run can be repeated.
  *Example, q006: "My mom turns 65 on March 12. When can she sign up for Medicare without paying a
  penalty, and when would her coverage start?"* The question gives no year. The agent first tried
  a birth year of 1961, saw from the result that the window had already closed, and tried 1962.
  Its answer gives the Initial Enrollment Period as December 1, 2026 through June 30, 2027 (page
  17), with coverage starting March 1, 2027 for anyone who signs up from December to February, and
  on the first day of the month after sign-up for March to June.

Every turn the model must call at least one tool (`tool_choice` is `any`): one of the two, or
`record_answer`, the same validated call part 1 uses to return an answer. It may call several at
once. After `AGENT_MAX_TOOL_TURNS=4` turns of tool calls, the next turn has to be `record_answer`.
The answer is then checked exactly as `ask` checks it: a citation to a passage the model was not
given is dropped, and the pages come from the database. Every tool call, with its arguments and
result, is stored with the answer, so part 4 can assert on it. The scoring pass adds each tool
result, exactly as the model received it, to the passages that context recall, context precision
and faithfulness read.

**The `agent` row.** The `agent` configuration is the part 2 winner, the `sections` chunk set with
the Cohere re-ranker, plus the two tools. Its retrieval is identical to `sections+rerank`'s, so
any difference between the two rows comes from the tools.

**Two new columns.** *Cost per query* is the mean, over all 40 questions of the run, of the trace's
cost at list prices; the six questions the handbook does not answer are included, because they cost
money too. The judge's calls in the scoring pass are not included: they are evaluation cost, not
serving cost. *p95 latency* is the nearest-rank 95th percentile of each question's wall time,
which for 40 questions is the 38th when they are sorted from fastest to slowest. Both are `—`
unless every question of the run has a trace with a cost. Latency is measured on one machine on
one day, so it compares the rows of one scoreboard and nothing more. `evals/scoreboard.md` adds
three tables that split the numbers: cost and latency per row, with the generations per query and
the number of fallbacks and skipped re-ranks; the time of each step (retriever, generation,
tools); and which questions called which tool.

**Checking the file against Langfuse.** `python -m evals.traces verify <results file>` reads each
question's trace back from Langfuse and compares it with what the results file stores: input and
output tokens must match exactly, and the cost within a ten-thousandth of a dollar. A trace that
is missing or does not match yet is asked for again for up to 30 seconds, since Langfuse takes a
few seconds to ingest a trace. It calls Langfuse only, never Bedrock.

**Hypotheses, committed first.** As in part 2, I wrote down four predictions before any part 3 run
and committed them as the part 3 section of `evals/HYPOTHESES.md`. They name the questions I
expected to call tools, so they can fail in public. The findings below judge each one.

### Run it end to end

Part 3 runs on part 2's setup: the same three Bedrock models and the judge, and `AWS_PROFILE`
exported in the shell, not set in `.env`. Sending traces to Langfuse needs a project's three values
in `.env`, as described above; everything below also works with `TRACING_PROVIDER=none`, except
`verify`, which then has nothing to compare.

```bash
export AWS_PROFILE=your-bedrock-profile          # boto3 reads this from the environment, not .env

# One question, each way. Both call Bedrock and print the answer and what it cost, and, when
# tracing to Langfuse, the trace's id and link. `agent` also prints every tool call first.
uv run fineprint ask "Dad has been an inpatient in the hospital for 80 days straight in the same benefit period. What is he paying per day now, and what happens if he's still there past 90 days?"
uv run fineprint agent "Dad has been an inpatient in the hospital for 80 days straight in the same benefit period. What is he paying per day now, and what happens if he's still there past 90 days?"
uv run fineprint agent --as-of 2026-10-23 "My mom turns 65 on March 12. When can she sign up for Medicare without paying a penalty, and when would her coverage start?"

# The same over HTTP; POST /agent takes the question, top_k and as_of.
uv run fineprint serve
curl -s localhost:8000/agent -H 'content-type: application/json' \
  -d '{"question": "What does Part A cost me for day 80 of a hospital stay?"}'   # second terminal

# A failure on purpose: the first answer falls back to Sonnet 5 and says so, the next does not.
FAULT_INJECTION=chat:unavailable:once uv run fineprint serve

# Two questions of the agent run, written to a scratch directory. --only needs a --results-dir
# other than the default, and such a file never becomes a scoreboard row.
uv run python -m evals.run_golden_set --config agent --only q001,q006 --results-dir /tmp/fineprint-smoke

# The real run, then the judge's pass, the check against Langfuse, and the scoreboard.
TRACING_PROVIDER=langfuse uv run python -m evals.run_golden_set --config agent
uv run python -m evals.score evals/results/<run_id>.json
uv run python -m evals.traces verify evals/results/<run_id>.json
uv run python -m evals.scoreboard

# Read only: the judge's stored working behind one question, and the hand review of a run.
uv run python -m evals.score evals/results/20261023T123658Z_agent.json --explain q029
uv run python -m evals.review evals/results/<run_id>.json
```

These call Bedrock: `ask`, `agent`, a request to `/ask` or `/agent` (and to `/search` in any mode
but `lexical`), every `run_golden_set` run, and `evals.score` on a file that has unscored
questions. `evals.traces verify` calls Langfuse and nothing else. `--explain` on a question the
file has already scored, `evals.review` and `evals.scoreboard` read files and call nothing. A full
`agent` run is 40 questions through the answer model with up to four tool turns each, plus the
scoring pass, so it costs real money; 40 × the row's cost per query is the serving part. The three
traced runs of this part are the `sections`, `sections+rerank` and `agent` rows.

### Findings

Every aggregate below is quoted from the generated block above or from the detail tables in
`evals/scoreboard.md`, and every per-question fact comes from the results files in `evals/results/`.
The scoreboard shows the latest run of each configuration, so its `sections`, `sections+rerank` and
`agent` rows are the three traced runs, `20261023T122309Z_sections`,
`20261023T122954Z_sections+rerank` and `20261023T123658Z_agent`.

**H1 — where the time goes.** Predicted: on `sections+rerank`, model generation is more than 80% of

On the `agent` row the tools take 0.0 s at p50 and at p95, as they should, being local Python.

**H2 — which questions call tools.** Predicted: `lookup_cost_figure` on the eight questions whose

- On q026, the hernia repair ("Exactly how many dollars will he owe for it?"), the answer says the

**H3 — what the tools cost.** Predicted: the `agent` row's cost per query and its p95 latency are

makes 1.60 answer-model calls per question on average, against 1.00. The p95 latency is 15.9 s
against 13.6 s, about 1.2 times (15.9 / 13.6), so that part is not. The median went from 10.2 s to
12.3 s and the slowest question from 13.9 s to 17.1 s. Page hit@5 is 100.0% on both, as it has to
be with identical retrieval. One more line of the same table needs explaining: `sections`, with no
re-ranker, costs more per query, $0.0515, than `sections+rerank`, $0.0494, though the re-rank is an
extra paid call. The answer call's input tokens, averaged over each results file, are higher on
`sections`, and more than make up for the re-rank's price.

**H4 — faithfulness.** Predicted: the `agent` row's faithfulness is at or above `sections+rerank`'s,
because the figures it states come from a checked table and each tool result is scored as context.
**Not held, narrowly.** It is 0.96 against 0.97, a difference of one hundredth on a metric that is
a judge's estimate. By question type the agent is higher on `table` questions (0.98 against 0.97)
and lower on `lookup` (0.96 against 0.97) and `multi_section` (0.94 against 0.98). To see what was
counted unsupported I read the working behind the agent's three lowest scores with `--explain`:
q029 (0.80), q016 (0.86) and q013 (0.88). None of the unsupported claims is a figure, and the
amounts these answers state were marked supported. They are of two kinds that part 2's findings
already describe. Some are details of the asker's situation worked into the answer, which the
claim check cannot see because it is shown the passages and the claims but not the question (on
q016 that Dad's Part B started in January 2026, and on q013 that he was first eligible at 65).
Others are a plain-language gloss the passages do not spell out ("at least as good as Medicare's"
for creditable drug coverage); and on q029 a start date worded for Medicare Advantage plans was
applied to drug coverage. So the tools did not raise faithfulness here, because what lowers it is
not a wrong figure.

**The answers, by hand.** I reviewed all 40 `agent` answers with `python -m evals.review`: 97.5%
pass (40 reviewed), and the one fail is q008. Its answer names the right month, July, for the last
health savings account contribution, but dates the birthday and the enrollment period to 2026. The
run's pinned date was October 23, 2026, after that year's August 14, so the next birthday is in
2027. The cause is visible in the file: the question gives no birth year, the agent called the
enrollment tool with 1961, the tool returned a window that ended in November 2026, and the answer
was written from it. On q006, which has the same shape, the agent saw that the window had closed
and tried again with 1962. The `hybrid` row's 85.0% is not a like-for-like comparison: that run
used the other chunk set and no re-ranker.

**What the traces showed about failures.** Each of the three runs had 0 fallbacks, and the two
with a re-ranker had 0 skipped re-ranks. So the fallback and degraded paths are shown only by the
tests and the `FAULT_INJECTION` switch, not by these runs, and nothing here measures how often
Bedrock fails. `evals.traces verify` matched all 40 traces of each run, tokens exactly and cost
within a ten-thousandth of a dollar, so the cost and latency columns agree with what Langfuse
holds.

**Part 2's rows were run again.** The part 2 `sections` and `sections+rerank` results predate
tracing, so their cost and latency cells could only be filled by running them again with it on.
Retrieval repeated: page hit@5 is 97.1% and 100.0% in both the old and the new runs. The
answer-side scores moved by a hundredth or two, because the answers are written afresh and judged
again. Computed the same way from the old and the new results files, the figures are, for
`sections`, context recall 0.82 then 0.80, faithfulness 0.95 then 0.94 and answer relevance 0.55
then 0.56, with context precision 0.74 both times; and for `sections+rerank`, context recall 0.94
then 0.93 and answer relevance 0.58 then 0.57, with context precision 0.90 and faithfulness 0.97
both times. The part 2 findings above quote the old runs and are not changed by this; the block
above shows the new ones. I did not separate the answer model's variation from the judge's.

## The corpus

"Medicare & You" is the handbook the Centers for Medicare & Medicaid Services mails to every
Medicare household each autumn: 128 pages covering enrollment, what each part covers, costs,
Medicare Advantage, Medigap, Part D, and where to get help. It is a U.S. government publication in
the public domain, and it is a good RAG test corpus precisely because it is awkward — two-column
comparison tables, cost figures that change every year, cross-references by page number, and a
five-page index.

The download script pins the file by sha256 and fetches it from the Internet Archive rather than
from medicare.gov. Two reasons:

- medicare.gov serves the handbook at a single unversioned URL, and that URL has served the 2027
  edition since September 2026. CMS keeps no public archive of prior-year handbooks.
- The 2026 edition exists in more than one printing, and they do not say the same thing. The
  September 2025 printing carries 2025 dollar amounts; the January 2026 printing carries the final
  2026 amounts. A cover that says "2026" is not enough. Pinning the hash is what makes an expected
  answer in the golden set mean something.

The PDF is not committed. `data/` is gitignored and the script fetches the file on demand,
verifying the hash before it writes anything into place.
